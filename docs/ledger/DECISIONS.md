| D-18 | Workspace `members` lists only `core/crates/*` until P03 creates `server/crates`. Wire design choices in sg-common: the ratchet header is a fixed 41-byte binary layout (canonical associated data by construction); the envelope is `version byte || protobuf body` and the decoder re-encodes and compares so unknown fields and non-canonical encodings are rejected; protobuf field 15 is reserved for franking and sealed-sender data and rejected in version 1; maximum envelope size is 128 KiB (Sargoshi decision, not in Prompt B). | Cargo refuses a glob over a missing directory. Strict canonical parsing removes malleability. |
| D-19 | Prompt B's `cargo audit` CI step is covered by `cargo deny check advisories` (RustSec database). A new tool `tools/check-dep-age.mjs` enforces the 14-day rule for every locked crate, transitive ones included. | One advisory tool is enough; the age rule was being violated by Cargo's resolver and needed a real check. |
| D-20 | The streaming AEAD adds a per-stream key: HKDF-SHA256(salt = random 16-byte stream id, ikm = master key, info = "Sargoshi/Stream/v1"). Prompt B only asks for a per-chunk nonce counter and a final-chunk flag in the associated data; the same recovery-derived backup key is reused across many backups, so a bare counter nonce would repeat (key, nonce) pairs across backups. The new label `INFO_STREAM` is not in the blueprint. Chunk index, chunk size, final flag and caller data are all in the associated data. | Prevents nonce reuse across streams under one master key. Listed for cryptographer review. |
| D-21 | ML-KEM-768 comes from RustCrypto `ml-kem` 0.3.4 (stable 0.3 line, 24 days old) rather than `libcrux-ml-kem` (only 0.0.x releases, newest 5 days old at the time of checking). Neither is known to be independently audited. The secret key is stored as its 64-byte seed. The key is checked against all 80 NIST ACVP ML-KEM-768 vectors. | Stable line, fewer dependencies, known-answer tests pass. Reassess before launch. |
| D-22 | Ed25519 public keys must be in the prime-order subgroup: `VerifyingKey::from_bytes` rejects small-order and mixed-order keys using the library's `is_small_order` and `is_torsion_free`, and verification is strict. The library's strict verifier alone accepted a mixed-order key (Wycheproof tc 160); Wycheproof marks those cases "acceptable", and honest keys are never mixed-order. | Removes a class of key-substitution oddities at no cost to honest peers. |
| D-23 | Cargo feature `deterministic-kat` of sg-crypto (off by default, enabled only by sg-testvectors) exposes deterministic ML-KEM encapsulation and a fixed-stream-id stream constructor so NIST vectors and the written construction can be reproduced. App builds never enable it. | Known-answer testing needs fixed randomness. |
| D-24 | X25519 and Ed25519 use the 3.x and 5.x dalek generation, chacha20poly1305 0.11, hkdf 0.13 and sha2 0.11: the newest stable releases that were at least 14 days old, not the older 2.x/0.10 lines. | Stay on maintained lines; API verified from source and by known-answer tests. |
| D-25 | Responder state: `accept` deletes the used one-time prekey and remembers the initiator's ephemeral key (the 4,096 most recent) to reject replays, because Prompt B requires replay rejection but a deleted one-time prekey cannot stop a replay of a message that used none. The core therefore returns updated state, and the FFI `session_accept` returns the updated prekey blob in addition to the session blob and the consumed one-time prekey identifiers listed in Prompt B. The caller persists it only after the first ratchet message decrypts. | A replay defence that works when one-time prekeys are exhausted. |
| D-26 | Prekey signatures are never stored; they are recomputed from the identity (Ed25519 is deterministic). The post-quantum signed prekey is one reusable key rotated by schedule (it is not one-time), so post-quantum forward secrecy of the initial handshake lasts until that key is rotated and pruned. | Fewer stored values and invariants; the limitation is stated in THREAT_MODEL.md. |
| D-27 | The two required identifiers of the initial header have explicit presence on the wire and are rejected when absent; the optional one-time prekey identifier may be absent. Bundles and headers are canonical protobuf; the single boundary truncation that drops the trailing optional field is a documented protobuf property, tested to never equal the original. | A missing required field must not silently become identifier 0. |
